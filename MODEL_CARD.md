# Model Card: Return-Risk Scorer

## Intended use

**Advisory scoring only.** At order-placement time, this model outputs a
probability that an order will later be returned. That score is meant to
route a *subset* of orders to a lightweight human/ops review step (e.g. a
size-confirmation nudge, restricted payment method, or extra packaging) - it
is **not** an automated order-blocking or order-cancellation system. See
[PROBLEM_STATEMENT.md](PROBLEM_STATEMENT.md) for the full decision context.

### Out-of-scope use

- **Not** a fraud/chargeback detector - a different class of loss with
  different features and cost structure.
- **Not** a substitute for manual review on flagged orders - the score routes
  to review, it does not deny service.
- **Not** calibrated for literal probability statements to customers or
  regulators (see Calibration, below) - use it for ranking/thresholding only.
- **Not validated on real transaction data** - trained and evaluated entirely
  on synthetic data (see Training data, below); must be re-validated against
  real order/return history before any production use.

## Training data summary

- 9,000 synthetic orders, generated by [src/generate_data.py](src/generate_data.py)
  (fixed seed=42), with return rate calibrated to **22.6%** - inside the
  15-30% range commonly cited for fashion/apparel e-commerce, and above the
  lower rates typical of electronics/grocery, reflecting this dataset's mixed
  category composition.
- Correlations are built in deliberately, not left to chance: new-account
  status, historical return rate, fit-sensitive categories (fashion/footwear),
  discount size, delivery lateness, and COD payment all carry real log-odds
  weight in the label-generating process, including 3 explicit interaction
  effects (new-account x high-value, fit-category x high-discount, COD x
  late-delivery).
- ~6% label noise and ~2.5% missingness in `actual_delivery_days` are injected
  deliberately, so the ceiling on achievable performance is realistic rather
  than artificially perfect.
- **Known limitation:** because this is synthetic data, the model has learned
  *this dataset's* encoded assumptions about what drives returns, not
  necessarily the real-world magnitudes. Feature *directions* (new account ->
  higher risk, fit-sensitive category -> higher risk, etc.) are standard,
  well-documented retail patterns; the exact coefficients are not
  production-calibrated.

Model selection process (CV comparison of Logistic Regression / Random
Forest / LightGBM, imbalance-handling comparison, Optuna tuning) is in
[reports/model_comparison.csv](reports/model_comparison.csv),
[reports/imbalance_comparison.csv](reports/imbalance_comparison.csv), and

**Logistic regression won on both CV PR-AUC and interpretability** - no
trade-off was needed. This is explained in detail there: the synthetic
data-generating process is log-odds-linear with its interaction effects
already materialized as explicit columns, which removes the structural
advantage tree ensembles would otherwise have.

### Calibration note (read before treating the score as a literal probability)

The model is well **rank-ordered** (monotonic - higher score reliably means
higher risk) but **not well-calibrated in absolute terms**: predicted
probabilities run systematically higher than observed frequencies (e.g. a
~0.8 predicted score corresponds to only ~55% observed return rate in the
held-out test set - see
[reports/final/calibration_curve.png](reports/final/calibration_curve.png)).
This is an expected side effect of `class_weight='balanced'`, which reweights
the training loss and shifts predicted probabilities away from the true base
rate. **Use the score for ranking and thresholding, not as a literal
"X% chance of return."** A production deployment wanting calibrated absolute
probabilities should apply isotonic or Platt recalibration on top of this
model's raw output.

## Chosen threshold and cost reasoning

Cost assumptions (explicit, stated in
[src/evaluate.py](src/evaluate.py)):
- False positive (legitimate order wrongly flagged): **Rs 50** - review-queue
  friction/support overhead; the order still ships.
- False negative (a real return ships un-flagged): **Rs 350** - reverse
  shipping + restocking/inspection labor + lost margin.

This 7:1 cost ratio correctly pushes the optimal operating threshold well
below the naive 0.5 default. The threshold was selected by minimizing total
expected cost over 5-fold out-of-fold predictions on the **training set
only** (never the test set, to avoid threshold-leakage) - see
[reports/final/cost_curve.png](reports/final/cost_curve.png). Chosen
threshold: **0.35**, which reduced expected cost by 13.4% versus the naive
0.5 threshold on that same training-OOF data.

## Known failure modes

From [ROBUSTNESS.md](ROBUSTNESS.md):

- **Not calibrated for absolute probability** (see above) - rank-ordering is
  reliable, literal percentages are not.
- **Low precision by design at the chosen threshold** (0.27) - the cost
  model intentionally accepts many false positives to avoid missing costly
  false negatives; a reviewer expecting a "confident" flag list will see a
  lot of low-risk orders mixed in. This is the correct trade-off *given the
  stated cost assumptions* - if the real friction cost of a false positive is
  higher than Rs 50 (e.g. flags actually delay shipment materially), the
  threshold should move up and precision will improve at recall's expense.
- **Synthetic-data ceiling**: real-world return drivers not represented in
  the generator (e.g. product-specific defect rates, seasonal returns,
  region-specific logistics issues) are unknown to this model.
- **Single-seller assumption**: no merchant-level aggregate feature exists,
  since the synthetic data models one storefront (see
  [FEATURE_DICTIONARY.md](FEATURE_DICTIONARY.md)).
- Stress tests (4/4 passed) confirm the model does not flag purely on one
  feature (new-account alone or high-value alone), but only 4 handcrafted
  cases were tested - this is not exhaustive adversarial coverage.
